# The declaration index and the similarity gate

`cmd/declindex` answers questions about a built Lean project and protects the concept registry that its owners share. The command's help is the short command reference; this document describes the persisted data and the landing contracts. The container acceptance drivers are in [e2e/README.md](e2e/README.md).

## Configuration and connection

Each index is one schema of a Postgres database that many indexes share. The configuration file names the schema; no configuration file holds a connection string.

| Key | What it names |
| --- | --- |
| `index` | the schema of this index: a lower-case letter, then lower-case letters, digits and `_`, at most 48 characters, and none of `pg_*`, `public` or `information_schema`. Every command that opens the index needs it. |
| `state` | the local directory of the exporter build (`<state>/exporter`) and of the registry's forms module (`<state>/forms`), relative to the configuration file's directory. It must resolve outside the tree, so that nothing the index or the gate builds can dirty the tree. Without it, the state is `<user cache directory>/declindex/<index>`. |
| `reader` | the read-only role that a refresh grants `USAGE` on the schema and `SELECT` on its tables. Empty grants nothing. |

The connection string comes from the variable `DECLINDEX_DSN`, or from the file that `--index-dsn-file FILE` names, whose trimmed contents win over the variable. `refresh` runs with a login that owns the schema; the queries, `status`, `land-hash`, `gate` and `ledger` run with the `reader` login. `ledger` keeps its own connection to the ledger, another database, from `LEDGER_DSN` or `--dsn-file`.

The key `db` and the flag `--db`, which named the index's file, are refused: `db: was removed: the index is a Postgres schema; set index: and pass DECLINDEX_DSN or --index-dsn-file`.

Global options come before the command:

| Option | Effect |
| --- | --- |
| `--config FILE` | the configuration file, or `DECLINDEX_CONFIG` |
| `--index NAME` | the schema, overriding `index`, so that one configuration in a tree serves a main and a test index |
| `--index-dsn-file FILE` | the connection string, from a file |
| `--state DIR` | the state directory, overriding `state` |
| `--json` | answer as JSON, where the command answers in JSON |

A command that opens the index without a schema name or a connection string is a usage error, exit 2. A failed connection to the index's database (no route, a refused or dropped connection, a server that restarts) exits 75 in every command, with `declindex: the index's database is unreachable: …`, so that the landing program runs that hook again rather than count a defect. `declindex --help` lists every command's exit codes.

The reach walk reads one index, `edges_owner`, which carries every column it reads, so a walk of the declaration that a whole tree uses never touches the table: that is 24 % of its time (3.27 s to 2.63 s on the copy's index). One entry of that index therefore holds four names and a kind, and a Postgres B-tree entry holds at most 2,704 bytes. A tree whose edge would exceed it is refused as an index defect that names the declaration and its length, never as a failure inside the database. The reference part is measured before its write, so such a tree leaves the index as it was; a name found in the compiled part leaves the reference part written and the index owing a compiled part, which every reader of a fact refuses, as a failed exporter does. Every indexed name is measured where it is written: a module, a declaration, a constant and its conclusion, an atom, a concept, and a clash with the module that read it and the module that declares it. The longest entry each table holds for the copy's tree, against the 2,600-byte limit: edges 479 bytes, decls 399, consts 231, uses 227, atoms 182. So the limit is more than five times the longest entry that tree has today; when a tree approaches it, the index must either drop the carried columns (and give back that 24 %) or key the walk by something shorter than a name.

Nothing of the index lives in a Postgres session. The shared server pools transactions on every route it offers (Cloud SQL's managed connection pooling, which the Auth Proxy reaches too), so each transaction may get another server backend: a startup parameter the pooler does not carry is refused at connect (`FATAL: unsupported startup parameter: search_path`, SQLSTATE 08P01), a session's `SET` would reach another client, and a session's advisory lock would stay on a backend the next transaction does not get. Measured on 2026-10-25: a refresh of 52,548 modules wrote its reference part, and 13 minutes later its compiled part met another backend, where its schema was not named (`relation "consts" does not exist`). So every statement names the index's schema in its own transaction (`SET LOCAL search_path`), each write transaction takes the index's lock for itself (`pg_advisory_xact_lock`, given back by the commit or the rollback), and no command prepares a statement by name unless its connection string names another `default_query_exec_mode`.

What a database lock cannot guard is the indexed tree, which a refresh fetches, checks out, builds and reads over many transactions, and which `gate` and `ledger` read for a whole run. That is a lock of the machine that holds the tree: the file `tree.lock` in the index's state directory (`state:`), taken exclusive by `refresh` and shared by `gate` and `ledger` (`land-hash` and the queries read the index alone and take nothing). Two refreshes on one machine therefore run one after the other, and a gate waits for the whole refresh, build included; two refreshes of one index from different machines are serialised by the index's lock, one write transaction at a time.

## Index data and storage

The index has two parts, in a schema of its own on a shared Postgres server:

- The `.ilean` part records declarations, source positions, direct uses, and declaration edges. It also records `sources`: every indexed Lean source path and the Git blob ID of the bytes that the index read. A changed source can therefore be distinguished from a source that the index already read.
- The compiled part reads `.olean` files with an exporter built by the tree's Lean toolchain. It records each constant's printed type, compiled statement hash, the heads of its explicit binders' types and of its conclusion, relation atoms, and the registry facts that its statement states. A head is the constant applied at the top of a type, past the type's own binders, any `let` or `have`, any default-value or tactic annotation and any metadata, also metadata inside an annotation, read from the elaborated type, so it is a full name however the source wrote it; a type whose head is a variable, a sort or a lambda has none.

The index metadata has `commit`, the Git commit it read, and `compiled_commit`, the commit whose compiled part it holds; the gate and the post-landing recheck refuse an index whose two differ. The `landings` table records each refresh that moved the index to another commit: that commit and the commit it replaced. The post-landing registry check of a landing compares those two commits, however many landings came after it. A module whose source is newer than its build, or whose recorded declaration position no longer holds its name, is unreadable until a build replaces the output; affected queries exit 3. A tree that is not a Git work tree has no commit: `refresh` reads it and records no commit, the queries and `status` print a note, and `gate` and `ledger`, which compare the index's commit with the tree's, exit 3.

The index records its schema version, which changes whenever what an index holds changes. After an upgrade to a `declindex` of another schema version, the next `refresh` rebuilds the index from nothing; until it has, `gate`, `ledger` and `land-hash` refuse the index with exit 3 and name that refresh.

The index and the contract ledger are separate, in separate schemas and usually separate databases. The index's schema holds the declaration, use, edge, import, compiled-constant, atom, fact, source and metadata tables, and a reach query walks the edge table itself: there is no graph file beside the index. The ledger holds contract owners, statement hashes, versions, and change-lock reads. One index is one schema, named by `index:` and made by `refresh`, so that many projects and many machines read one server while a landing rewrites only the schema of the index it refreshed. The connection string comes from `DECLINDEX_DSN` or `--index-dsn-file`, never from a file in the indexed tree; `reader:` names a role that `refresh` grants the schema's reads to, for the machines that only query.

A declaration is its module and its full name: two modules that are never imported together can each declare one name, and the index keeps both apart. Each use records the module that Lean recorded for the constant it uses, and each compiled constant, atom and fact its module. A use of a part Lean generated from a declaration (a field, a constructor, an equation lemma) counts for the declaration of the longest prefix of its name that its module declares; for an equation lemma that Lean made in the module that uses it, the declaration in that module's imports. `where`, `hash`, `users`, `states` and `same` answer each declaration with its own module, place, hash, users, reach and atoms. `same NAME` prints, for each declaration NAME resolves to, `{"declaration", "module", "at", "same": [declarations]}`. `states CONCEPT` prints, for each constant that states the concept's fact, `{"declaration", "declaration_module", "constant", "module", "how", "at"}`, and its text form counts the declarations by module and name. The ledger's contract key, `land-hash` and the gate's taken-name check stay by name: a name declared twice is ambiguous there.

Each edge records that declaration in the row itself, resolved when the refresh writes the row. A later landing can move it without touching the row's own module: a module that declares the name, or an import that brings another declaration of it into the closure. The refresh that lands such a change resolves again, and writes, exactly the rows that moved: those whose constant is at or below a declaration name it added to or removed from a module, and those whose owner the imports decided in a module whose import closure it changed. So an index that landings built answers as one built from nothing, and a landing that adds and removes no declaration and changes no import writes no row of another module at all.

Lean imports a second declaration of a name only when one of the two subsumes the other: the same type, and both theorems or a theorem and an axiom (two axioms only when a cheap check finds their type a proposition). Every declaration in a module's imports loaded together when the module built. Among theorems and at most one axiom the relation is transitive and does not depend on the order, so two sets of declarations of a name load together when they share one, or when Lean imports one module of each together. Before it keeps a module from the forms for a name, the compiled step asks Lean that: an exporter run that imports the two declaring modules and reads nothing, once for each pair of modules, its count on stderr (`index: N pairs of modules that declare one name checked with Lean, M import together`). So two copies of one theorem, wherever they are, keep no module from the forms. Two axioms may have loaded only because a theorem came before them, so two sets that hold two axioms between them load together when they are the same set, or when Lean also imports each pair of the axioms' modules together, which makes the order irrelevant: two `axiom dup : True` do, two axioms that only a theorem reconciles do not. A module that declares a name imports no other declaration of it, so each such check meets exactly its two declarations. The compiled step reads modules in groups, with the registry's forms, where for each name the group's declarations and each module's load together by that rule. A module whose declarations of a name do not load together with the forms' imports' declarations of it is read without the forms: it states no fact of a written form, and none of a concept whose name two modules declare. Each such module is an index defect, a duplicate declaration in the tree. The index records it with its clashes; `refresh` and `status` (also with `--json`) name each module and the modules that declare the name on each side on stderr; `states` and `gate` give their count on stderr, and the gate's verdict as `modules_without_forms`; `declindex --json status`, and `declindex --json refresh` when it reads the build, list them as `without_forms` (`{"module", "name", "declared_in", "forms_declared_in"}`). Each refresh that reads the build reads such a module again, so it joins the forms once the clash leaves the tree. A module whose reference file can no longer be read leaves the index with its compiled rows and its clashes.

When Lean imports two declarations of one name as one constant, it keeps the module that loaded first, which depends on the modules that one exporter run imports together. So a compiled hash counts a reference to a public theorem, or to an axiom whose type is a proposition (the only constants Lean merges), by its name and the hash of its type, and a reference to any other constant by its name and the module that declares it. A statement's hash is then the same after a refresh that read its module alone, one that read it with every other module, and in a proposal that imports one of the copies.

What a module states of a written form, and whether it loads with the forms at all, depends on the forms' whole import closure. The compiled part therefore records, with the exporter's version and the forms' text, each module of that closure and the key of its build. When a module of the closure imports another module or is built anew, the next refresh reads every module again, as it does after a change of the forms.

The grouping sees only the declarations and imports that the index read from the library directory's reference files. It does not see a dependency outside that directory (a Lake package), nor a declaration that Lean leaves out of a reference file's `decls` map: with Lean 4.36, `theorem t (P : Prop) (h : P) : P` and `theorem t : ∀ P : Prop, P → P` are not there, while `theorem t : ∀ (α : Type) (a : α), a = a` is. A duplicate among those cannot be grouped apart in advance. When one clashes, the exporter fails with "environment already contains" and `refresh` exits 3; it drops no module silently.

## Concept registry

The registry is format 2 and is rooted at the project tree's configured `registry` directory:

```text
registry/
├── registry.yaml
└── concepts/
    └── <key>.yaml
```

`registry.yaml` contains `version: 2` and optional imports and opens for the forms module. Each concept file has one name, home file, one-sentence meaning, optional `extends` and forms, and, for gate additions, the proposal ID, proposer, compiled hash, accepted-by decision, accepted near matches, accepted duplicates (`accepted_duplicates`: the indexed declarations, none a registered concept, whose compiled statement equals the concept's and which `--accepted-by` admitted it beside, sorted; the loader refuses the key in a file without `accepted_by`, `compiled_hash` and `source`), `declarations` (the constants that the stored source declares, as the gate compiled it: the concept's own, and its proposal's helpers and their parts, each named as it is once it lands in the home file), and stored source. The home file is the path of a `.lean` file relative to the tree, as the index names a module's file: slash-separated, inside the tree, with no `.` or `..` step and no repeated or trailing slash, for example `Sub/Frame.lean`. The loader refuses a concept file with another home, and the gate refuses such a proposal with exit 3, before it compiles anything. A concept with a compiled hash is keyed as `concepts/<compiled_hash>.yaml`; a librarian-written concept without one is keyed as `concepts/<name>.yaml`.

A concept with forms and no stored source is matched through its forms, whether or not the index declares its name. A concept with no form is matched through its own declaration's body, so it is matched only once the index declares it. A concept's declaration is the one of its name in the module of its `home` file; another module's declaration of that name is not the concept's. A gate addition that has not landed is compiled from its stored source by the gate alone.

One concept per file lets an owner open a change lock on only the proposed addition. The gate writes no registry file. `addition.path` is relative to the repository root and slash-separated, for example `registry/concepts/<compiled_hash>.yaml`, so it names the same file in every worktree. When the configured tree is a directory below the repository's root, the path starts with that directory, as `refresh` recorded it in the index (for example `proj/registry/concepts/<compiled_hash>.yaml`). The owner writes the returned `addition.content` to that path in its own worktree, opens or extends its migration with `ledger open --write <addition.path>`, and lands it normally.

The loader reports these registry defects: a concept file it refuses (YAML that does not decode, an unknown key, a concept that fails its checks, such as a two-sentence meaning), which it leaves out; duplicate names; duplicate compiled hashes; wrongly keyed files; missing `extends` targets; and an accepted duplicate that is a registered concept, whose file it keeps. The gate also reports a pending concept whose stored source the text filter or Lean refuses, and leaves it out of the forms. A defect is one concept's: `refresh` and `gate` report defects as notes and continue, and `ledger` reports them in its registry result and exits 1. Only a missing, malformed or format-1 `registry.yaml` stops them. A refused concept file still holds its path, and the name and compiled hash that its YAML gives, so the gate adds no concept that would take them: a proposal with its name (or with its key, when the file is keyed by a name) is `name-taken` and names the file, and a proposal whose compiled statement is its key or its recorded compiled hash exits 3, since its addition would replace or restate that file.

Stored source is untrusted input. Refresh and the ordinary registry forms module never compile it. Only the gate and the post-landing recheck compile stored source, after Lean's parser allow-list, with the rights of the user who runs them ([Untrusted source](#untrusted-source)).

## Similarity gate and librarian route

An owner runs:

```text
declindex --config <cfg> gate --proposer <owner-id> [--accepted-by <owner-id>] PROPOSAL.json
```

`PROPOSAL.json` has `id`, `concept` (`name`, `home`, `meaning`, and optional `extends`), and `source`, a Lean module that declares the concept. It carries no forms, and any `accepted_by`, `accepted_near`, `accepted_duplicates` or `declarations` it carries is ignored. Before deciding, the gate requires an index at the tree's HEAD whose compiled part is of that commit, and a registry directory without local changes once it has taken its snapshot of the registry at that commit. Failure of any of those checks is exit 3 with a cause on stderr and no librarian request. The verdict's `defects` list the registry's defects: every loader defect, and each pending concept that the decision left out of the forms because its stored source no longer compiles. The gate also prints them as notes.

`--accepted-by <owner-id>` gives the librarian's ruling, an owner id as `--proposer` takes it (a role such as `legion-linux-linux-32-architect`, not a link to the ruling, which is exit 2). It admits the proposal's near matches, which the addition records as `accepted_near`, and its exact duplicates of declarations that no concept registers, which the addition records as `accepted_duplicates`: the librarian ruled the new name the canonical one, or its own concept with an equal body. The verdict's `duplicates` lists every such copy, also when the gate refuses. It never admits a copy of a registered concept, landed or pending, or of one whose declaration the index holds outside its home file: that is still exit 1 and names the concept. With `--accepted-by`, a copy whose name a concept file that the loader refused holds is exit 3, since that file may be the copy's concept.

A declindex built before `accepted_duplicates` refuses a concept file that has it, as an unknown key, so every gate and `ledger` that reads the registry runs a build that knows the key before the first such file lands. A concept that was registered by hand for such a ruling (a file keyed by its name, with no compiled hash or source) is replaced by the gate's addition while its proposal is still unmerged: gate it with `--accepted-by`, and commit `addition.content` at `addition.path` in place of the hand-written file, since two files of one name are a duplicate-name defect. The gate reads the registry of the tree's HEAD, so the hand-written file on the proposal's branch does not stop it. Once the declaration has landed, the gate answers `name-taken`; leave the hand-written file as it is: its landed declaration still refuses later copies.

| Exit | Verdict | Owner action |
| --- | --- | --- |
| 0 | `added`: no registered fact or existing declaration states the proposal, or `--accepted-by` admits the near matches and copies that do. | Write and land the returned addition. |
| 1 | `refused`: the proposal is an exact duplicate, unless `--accepted-by` admits copies of unregistered declarations. | Use the named existing concept. |
| 3 | Unable to check, also when a concept file that the loader refused holds the proposal's compiled statement, or, with `--accepted-by`, a copy's name. | Keep the item open and retry after the cause is repaired or the index is refreshed. |
| 4 | `near`: a registered fact is restated. | Wait for the librarian's decision. |
| 5 | `name-taken`: a concept, a declaration or a concept file that the loader refused already has the proposal name. | Use that concept, or use another name for a different statement. |
| 2 | Usage error. | Correct the command invocation. |
| 75 | The index's database could not be reached. | Run the gate again. |

The comparison has no embedding threshold and no partial-atom threshold. Exact compiled hashes are refused, unless `--accepted-by` admits copies of declarations that no concept registers (above). Two statements have the same compiled hash when their elaborated terms are equal up to binder names, the declaration's own name (which a literal definition counts after all, below), and how a numeral of core Lean's `Nat` and `BitVec` instances is written (`7#64` and `7 : BitVec 64` agree). Any other numeral counts with its type and instance, since its instance gives its value: `@OfNat.ofNat Nat 7 ⟨9⟩` is 9, so it is not `@OfNat.ofNat Nat 7 ⟨10⟩`. Each constant that a statement names counts with the module that declares it, so a statement about A's `Value` is not one about B's `Value`, and a private name counts by the name its source writes. An inductive counts its constructors' names, each past the inductive's own (`walk` for `Mode.walk`), and their fields' names, so two enumerations are equal only when their constructors are named alike and in the same order: counted by their types alone, every enumeration would equal any other with as many constructors. A definition with no parameters whose value is a numeral or a literal and nothing else (`def size : Nat := 16`, and likewise `0#64`, `255 : UInt64`, `-3`, `'a'`, `0.5` or `"irq"`, whatever the instance) counts its own name too, since its type and value do not say what it denotes: it matches only a declaration of its own name, which the name check answers first (`name-taken`). Such a proposal is therefore never refused as a copy of another constant; the gate goes on to the registered facts, and two of one value get two addition paths. A definition whose value is anything more than a literal, a parameter or another constant among it, is still compared by its statement alone. A concept file records the hash the gate gave it, and a pending concept, added and not yet landed, is compared by the hash its stored source compiles to at each decision as well as by that record; the post-landing check accepts a record made by the formula before constructor and literal names counted (the exporter's `h0`), so a file the gate wrote before that change still lands. An auxiliary definition that elaboration made (a matcher, or a theorem that holds a proof abstracted out of a body, whose last name component Lean writes as `_proof_` and an index: `foo._proof_2`, or `rt._proof_1_3` in a recursive declaration) counts by its content, and an abstracted proof by its type alone. A matcher is one that Lean recorded as a matcher in its module (the exporter reads that record from the imported module, since it does not load environment extensions), and it gets no row of its own. A constant of another kind, or with another name, keeps its own identity, also when its name starts the same way (the constructors `Choice._proof_left` and `Pick.match_left`). In one module, elaboration reuses an earlier declaration's proof of the same type, and its matcher for the same patterns, so `def bar … := ⟨n - 1, Nat.sub_lt h Nat.one_pos⟩` names `foo._proof_2` and `def bar (n : Nat) : Nat := match n with …` can name `foo.match_1`, while a copy of `bar` gets its own, and the two still hash equal. A proposal, compiled as a module of its own, is hashed as of the module of its home file, so the declaration that lands there has the compiled hash that the gate recorded. A statement that directly states a registered form, or states it through a declaration in the proposal, is near. Form matching compares numerals only by the value they are written with, so it gives only near results. A proposal that the gate cannot compare is also near rather than accepted. `--accepted-by` records a librarian decision that a near proposal is new, or that a copy of unregistered declarations stands as its own concept; the resulting addition records `accepted_by`, `accepted_near` and `accepted_duplicates`.

For every near result, the configured `librarian: [cmd, args…]` receives:

```text
cmd args… --id <verdict-id> --proposer <owner-id> --proposal <file>
```

The file is mode 0600 in the gate's temporary work directory and is removed after the command exits. It contains fixed text, the deterministic ID and validated proposer outside a nonce-delimited block, and one JSON line inside the block. The JSON carries the verdict and the untrusted proposal. The command receives empty standard input. Exit 0 means delivery; another exit or a 120-second timeout makes the gate exit 3. The post-landing recheck sends the same envelope with `--id recheck-<added hash>-<other>` and `kind: "recheck"`; see `ledger` for who delivers it. `<added hash>` is the added concept's compiled hash. `<other>` is the other concept's compiled hash, or, for a librarian-written concept without one, `name.` followed by the hexadecimal of the name's UTF-8 bytes. So every recheck ID matches `^recheck-[A-Za-z0-9._:@/-]+$`, whatever characters a Lean name holds, and two pairs never share an ID.

### Untrusted source

The gate applies two controls before it compiles a proposed source or a pending concept's stored source; the post-landing recheck applies the second to an added concept's stored source, which has landed:

1. A text filter rejects obvious executable forms (`run_cmd`, `initialize`, `macro`, `native_decide`, an attribute that registers code, …). It leaves a `#` command such as `#eval` to the allow-list, since no text pass tells one from an Iris proof-mode pattern (`#Hinv`, also one that goes on to a line of its own) or a `#v[…]` literal.
2. Lean's parser allow-list admits declarations and limited surrounding syntax, refuses every other command (a `#` command among them) wherever it stands, and refuses forms that execute during elaboration.

Both controls are rules about content: a proposal holds declarations only. Once a source passes them, the gate compiles it and the exporter reads it with the rights of the user who runs the gate, in fresh directories below the gate's temporary work directory, with only the toolchain's environment (`PATH`, `LEAN_PATH`, `LEAN_SYSROOT`, `LANG`, and `HOME` and `TMPDIR` in that directory), so none of the caller's credentials or tokens reach Lean. The owners that propose concepts run the gate themselves, so a proposal's compile runs with the rights that its author already has there. When the allow-list refuses a proposal's source, or Lean rejects it, the gate exits 3 with the refusal or Lean's errors on stderr.

## Reading the index from another program

A program that checks changes against the index (the graph checks the landing program runs) reads it through this package, never through a database path or SQL of its own. It loads the project's configuration with `LoadConfig`, opens the index with `OpenReadOnlyConfig(ctx, cfg, IndexOnly)`, and refuses an incomplete index with `Store.CheckComplete`. One open store reads one state of the index for its whole life, so a refresh that commits meanwhile changes no answer it gives.

`Commit` and `ModulePaths` say which commit the index holds and where each module's source is. `DeclsInModules`, `DeclsNamed` and `DeclsShort` give declarations by module, full name or last name component, each sorted and without a key's repeats. `UsesOf` gives the recorded uses of each named declaration and of the parts Lean generated from it, each as often as the index records it however the names asked for overlap. `Imports` gives every module's direct imports. All of them read what the index took from the `.ilean` files.

The compiled constants are read with `ConstantsIn` (by module) and `ConstantsConcluding` (by conclusion head), after `CompiledCommit(ctx, true)` has accepted the index: each is the exporter's `Constant` as the index holds it, without its atoms, facts and `LegacyHash` (the gate and the post-landing check read that from the exporter itself). A program that compiles a changed module itself, into a scratch directory with `CompileModule` against the built tree's library directory and with the options the build gives each module, reads it with `ParseModule` and with the exporter (`BuildExporter`, then `Exporter.Run` with `Manifest.Types` and the scratch directory first in `Exporter.SearchPath`), and gets the same rows that the index would hold for that module. A module's row is its own declaration's whichever modules are read with it, also for a theorem that two modules declare and Lean merges.

## Landing interfaces

### Landing containers

The landing program's container contract decides each container's mounts and network. Every command that opens the index needs a route to the Postgres server and the connection string of its login; `refresh` writes the index with the owning login, the rest read it with the `reader` login. Besides `TMPDIR`, where `declindex` makes its registry snapshots, its proposal work and the toolchain runs' scratch directories, each command needs these writable places and nothing else:

| Command | Writes |
| --- | --- |
| `refresh` with `LAND_COMMIT` | The tree (fetch from `remote`, checkout, `build`), the index's schema on the server, and the state directory (`state:`), where it builds the exporter. |
| `ledger` | The `--emit` file, and the state directory only when its recheck of an added concept builds the exporter there, because no refresh with `lean.export` built it first. Otherwise the state directory can be read-only. |
| `gate` | The state directory only to build the exporter, when no refresh with `lean.export` built it there first. It writes nothing of the index. |
| `land-hash` | Nothing. It reads the index, `LAND_GIT_DIR` and `LAND_BUILD_DIR`; the state directory can be read-only. |

A refresh holds the index's advisory lock (`pg_advisory_lock`, keyed by the index's name) across the fetch, checkout, build, its reads of the tree and both of its writes, on one connection of its own: if that connection drops, the server gives up the lock and rolls back the open transaction together, and the command exits 75. `ledger` and `gate` read the tree as well as the index (its HEAD, the registry's commits, and the build that they compile against), which a refresh changes, so they hold that lock shared: they wait for a running refresh, including its build (at most `build_timeout`), and a refresh waits for them. `land-hash` and the queries (`where`, `users`, `hash`, `states`, `same`, `status`) answer from the index alone and take no lock: while a refresh fetches, checks out, builds and writes, they answer from the index of the refresh before. The recheck in `ledger` uses the exporter that `refresh` with `lean.export` built in the state directory.

Each reading command (`gate`, `ledger`, `land-hash`, `where`, `users`, `hash`, `states`, `same` and `status`) opens the index read-only and reads one snapshot of it, one repeatable-read transaction, from its start to its end. So a command never reads a write half done, nor rows of two refreshes: a command that began before a refresh's commit reads the index before it, and one that began after reads the new index. A command writes its output only after it has closed the index, so that a slow reader of its output holds no snapshot open.

A refresh writes the index in two transactions: the reference part (sources, modules, declarations, uses, edges and the landing record), then, with `lean.export`, the compiled part (types, compiled hashes, atoms and facts), after the exporter has run. A command that reads between the two, or after a compiled step that failed, reads the new commit's reference part and the previous commit's compiled part (`compiled_commit` differs from `commit`); `gate` and `ledger` meet that state only after a failed compiled step, since they wait for a running refresh. The readers of the compiled part refuse that index: `gate` exits 3, `ledger` exits 75 when its recheck of an added concept would read it, and `states` and `same` exit 3. Each names the two commits. `where`, `users`, `hash`, `status`, `land-hash`, and a `ledger` with no addition to recheck read the reference part only and answer from the new commit.

A refresh ends with one `VACUUM (ANALYZE, TRUNCATE false)` of the tables a query reads, on the connection that holds its lock, after both transactions commit. `COPY` leaves a table without statistics, so until autovacuum's nap ended a reader read the wrong plan: a reach of one declaration of a 2,000,000-edge probe took 1,876 ms with no statistics and about 1,500 ms with them, and 926 ms when a covering index let it read the index alone, which this schema does not have (a declaration's name has no bound, and such an index refuses an edge of two long names). The post-landing hooks and the owners' first queries run in that window. It does not truncate: a reader that opened after the commit holds the tables a landing emptied rows of, and the truncation would wait five seconds for each of them.

The configuration's absolute paths, such as the toolchain, `lean.cc`, `remote` and the owner map, must exist at the same paths inside the container. A container image with the pinned toolchain copies it from a worker image pinned by digest, as `e2e/Dockerfile` does (the required `LEAN_IMAGE` build argument; [e2e/README.md](e2e/README.md)).

Deployment requirement: the identity that pulls the worker image on the landing machine needs read access to the registry that holds it; without it the pull fails with HTTP 403. Grant that access, or copy the image by digest to a registry that identity can read, before the landing program builds these containers.

### `refresh`

The landing hook invokes:

```text
declindex --config <cfg> refresh && declindex --config <cfg> ledger --contracts-file <contracts> --emit <operations>
```

Global options such as `--config` come before the command. `<contracts>` is the ledger's contracts of the configured repository as a JSON array, and `<operations>` the file where `ledger` writes the registrations and near pairs for the landing program to apply ([`ledger`](#ledger)).

The landing program sets `LAND_COMMIT` and `LAND_PART`; `declindex` reads `LAND_COMMIT` and does not read `LAND_PART`. With a 40-hex lowercase `LAND_COMMIT`, `refresh` runs under the index's advisory lock, which it holds for the whole run ([Landing containers](#landing-containers)). It refuses tracked tree changes, recognizes an index that already covers the commit, fetches a missing commit from configured `remote`, checks out the commit, runs configured `build` within `build_timeout` (six hours by default), records `sources`, reads the reference files, and records the landing (the commit and the one it replaced). With `lean.export` it then reads the compiled part under the same lock. An index covers the commit only when it read that commit or a descendant completely: without unreadable modules, and with the compiled part when `lean.export` is on. So a retry after a failed build, reference read or compiled step runs again. A refresh queued behind another's lock ends when it gets SIGTERM, SIGINT or SIGHUP.

The remote can hold the landed commit under a ref that is not a branch, as a landing program's clone does, so the fetch asks for `LAND_COMMIT` by its id. Only when the remote refuses that (a server that allows only the tips it advertises) does it fetch the remote's branches; a refresh whose fetches both fail exits 75. The fetch writes refs only under `refs/declindex/remote/<pid>-<random>/`, a namespace of that run, and deletes those refs when the sync ends; the checkout is by hash. So refreshes in several worktrees of one repository, which share its refs, never move each other's refs.

`refresh` exits 0 after reading the build, 3 when it cannot safely read it, 75 for a failed fetch, build timeout, signalled build or unreachable index database, and 2 for usage. A configured build that exits nonzero exits 3. A registry defect is a note, not a failure. So is an index defect, a module read without the registry's forms: refresh exits 0 and names each such module and its clash on stderr, after this refresh and every later one until the clash is gone.

### `land-hash`

The landing program calls `declindex land-hash` twice for every registered contract:

1. At the base tree, with the index at that tree. Unchanged declarations are answered from the index; no candidate build directory is needed.
2. At the built candidate tree. For each source blob that differs from the indexed `sources` blob, `LAND_BUILD_DIR` must hold a fresh Lake `.ilean` and trace for that tree. The candidate answer gives the changed contract's candidate hash and path; unchanged declarations keep the indexed answer.

A declaration is answered from the index only when `LAND_TREE` has its source file with the same blob as the indexed `sources` row. A module that the index read without a `sources` row, such as an ignored source file, is not answered from the index.

The configured tree can be a directory below its repository's root. The index keys `sources` and declaration paths relative to the tree, and `refresh` records the tree's directory in the repository (`git rev-parse --show-prefix`). `land-hash` reads that directory from the index, never the configured tree: it lists the sources of `LAND_TREE` below that directory, compares them with the index by their tree-relative paths, and prints each `path` with the directory in front. For a tree at the repository's root the directory is empty.

A changed module's build output is fresh only when all of these hold:

- `LAND_BUILD_DIR` holds that module's source with exactly the candidate blob's bytes.
- Its `.ilean` is the output its Lake trace records: Lake's hash of the file equals the trace's `outputs.i`.
- A build trace's source input hash equals the blob's. A fetch trace, which Lake writes when its artifact cache serves the module, has no source input. It binds the outputs only, and the source only by being newer than it. A cache hit is still a legitimate result, because Lake serves one only when the key it computed from the module's inputs in that build matches.

So for a fetch trace, nothing in the build directory ties the outputs to the candidate's source. What keeps another build's `.ilean`, copied in together with its matching fetch trace, out of the answer is the landing program's contract: it builds the candidate in a fresh container that no agent can write. Any other output that fails these checks exits 3.

The command takes no positional arguments. Its environment is:

- `LAND_TREE`: the 40-hex Git object whose tree is being answered. Its tree is the repository's root tree, also when the configured tree is a directory below it.
- `LAND_GIT_DIR`: a Git directory that can read `LAND_TREE` and its blobs.
- `LAND_NAMES` or `LAND_NAMES_FILE`: a JSON array of distinct, non-empty, fully qualified names. A top-level declaration's full name has no dot, so a name need not contain one. The file form is required for large requests. If both are set, their arrays must be equal.
- `LAND_BUILD_DIR`: the candidate build root when a requested declaration is in a changed source file. It is the candidate's copy of the configured tree, so its sources are at their tree-relative paths.

On exit 0, each requested name produces one line in request order:

```text
name<TAB>hash<TAB>path
```

The `hash` is the 16-hex text statement hash and `path` is the repository-relative declaration path. The hash is the first 16 hex digits of the SHA-256 of the declaration's statement as written (a theorem's signature, a definition's whole text), with comments dropped and each run of white space between tokens collapsed to one space; a string or character literal keeps its own white space. An absent declaration is `name<TAB>absent<TAB>-`; an ambiguous declaration is `name<TAB>ambiguous<TAB><sorted,comma-joined paths>`. Exit 3 writes no stdout when the request, Git tree, source snapshot, candidate build, trace, or parsed declaration is unusable, or when a path that an answer line prints contains a tab, carriage return, newline, or comma. Such a character in a source path that no answer prints does not affect the call. Exit 75 writes none either, when the index's database cannot be reached. Exit 2 is a usage error.

### `ledger`

`ledger` checks the ledger only after the index is at the tree's HEAD. It opens the index read-only, over the index's own connection. It opens the ledger through `ledger.OpenExisting`: a database without every required schema version, or without the configured repository, is not changed and is unable to check. The ledger's DSN comes from `LEDGER_DSN` or `--dsn-file`, for an operator's check. The landing hook instead uses `--contracts-file FILE --emit FILE`; that mode never connects to the ledger or runs the librarian command, and `--dsn-file` with it is a usage error.

The contract check registers selected, owned declarations that the ledger lacks, then compares every ledger contract whose name has no `:` with the index by exact name across every module. It reports a changed hash as a defect, no declaration as gone, and multiple declarations as ambiguous. Names with `:` are non-Lean ledger contracts and are not compared with declarations.

The registry check reads the registry as committed at the index's commit, never the working tree, so a local edit after `refresh` does not change what it audits. It checks one landing: `LAND_COMMIT`, or the index's commit without it. It lists the files directly under `concepts/` with a `.yaml` extension (the files the registry loader reads) that the commits from the commit that landing's refresh replaced to that landing's commit added, with rename detection off, so a file added next to a deleted, similar one is an addition. When no refresh stopped at `LAND_COMMIT` (a later landing's refresh read it), the landing that read it rechecks its additions. When the landed build declares an added concept in the module of its home file, that declaration is the concept: its compiled hash must be the one the concept file records, else the landed declaration is not the one the gate added (a defect). That module is read again, as the gate reads a proposal, with the registry's forms and the compiled stored sources of the concepts that have not landed, so the facts of the concept and of the other `declarations` of its proposal in that module (its helpers, each with the parts Lean generated from it) are compared with every registered concept, landed or not. Another declaration of that module is not the proposal's, also one in the namespace of a listed one. Otherwise the concept is recompiled from its stored source, after Lean's parser allow-list, as the gate compiles a proposal; Lean refuses two definitions of one name, so the recheck's forms then import no module whose imports declare the concept, and a registered concept whose compiled constant is in such a module is compiled from its stored source, as a pending concept is. The check records additions by their paths from the repository's root (the paths the gate printed as `addition.path`, also for a tree below that root), loader and recheck defects (a stored source that Lean refuses or does not compile is one), near pairs, and an inability reason in the `registry` JSON member. Each near pair not suppressed by an accepted-near record goes to the librarian once:

- With `--emit`, the hook does not reach the ledger: after the registration lines, the emit file gets one line per near pair, `{"op":"librarian","id":"recheck-<added hash>-<other>","kind":"recheck","proposer":"<owner id of the added concept>","envelope":"<the text the librarian command would read from its --proposal file>"}`, for the landing program to deliver with the librarian command.
- With a ledger DSN, `ledger` runs the librarian command itself, as the gate does.

The JSON output is:

```json
{"commit":"…","contracts":{…},"registry":{"added":[],"defects":[],"near":[],"unable":""}}
```

The final stderr line counts contracts, registrations, contract defects, gone, unowned, ambiguous, and registry additions, near pairs, and defects. `ledger` exits 0 only when both checks are clean; 1 for a contract hash defect, gone, unowned, ambiguous contract, registry defect, or added near pair; 3 when it cannot check the contracts; 75 for a failed connection to the ledger or to the index's database, and when the registry recheck cannot run at all (no toolchain, a missing landing record, an exporter that does not run), whatever else it found, so that the landing program runs the check of that landing again; and 2 for usage.
